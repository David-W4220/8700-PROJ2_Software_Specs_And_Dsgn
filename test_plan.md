# Test Plan

This plan refines the eight acceptance criteria in the `cahoy` branch's `spec.md`. Requests use the proposed REST contracts in `contracts.md`; timestamps are fixed test inputs where the spec requires recording time. Successful requests use HTTP 200 unless the API contract specifies resource creation (HTTP 201). Rejected requests use HTTP 400 for quantity validation or HTTP 403 for authorization. The latter code is a proposed contract choice because the spec only says the action is denied.

## Spec gaps

- Every functional requirement FR-001 through FR-004 has at least one acceptance criterion, and every AC-001 through AC-008 cites at least one functional requirement. NFR1 through NFR8 are related to at least one criterion in the specification.
- **Role permissions:** NFR5 and FR-004 require an authorized conflict reviewer, but the spec does not define which roles are authorized. This blocks a concrete unauthorized test fixture/control.
- **Input types and errors:** quantity JSON type, coercion rules, error schema/status, and precedence when a request has multiple invalid fields are not defined.
- **Concurrency:** no rule specifies how simultaneous quantity updates are serialized or rejected.
- **Test data setup:** the spec and architecture describe initial inventory, Earth snapshots, pending updates, and conflicts, but do not define a contract for loading those Given states into an isolated test run. Tests need an agreed fixture/setup mechanism.
- **Conflict protocol:** the spec says competing edits to the same item must be kept, but does not define conflict identity/detection or how the conflict is retrieved for review.
- **Sync timing and failure behavior:** “when communication returns” is stated, but no synchronization time limit, retry schedule, or detailed failure response is defined.
- **Status and receipt semantics:** AC-006 says an update is marked synced after Earth accepts it, but the exact response fields and when the last-successful-sync timestamp changes are not specified.
- **AC-008 has an acceptance criterion without a defined role mapping**, although its requirement reference FR-004 exists.
- No acceptance criterion is orphaned from the functional requirements; there is no functional requirement without a cited acceptance criterion.
